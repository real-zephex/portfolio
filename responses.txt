## 📋 Issues Overview — Complete Breakdown

### 1️⃣ Missing Secure Referrer-Policy Header
- **Type:** Warning | **Priority:** Low | **Affects:** 100% of URLs (11 URLs)

**What it means:**  
The site does not set a `Referrer-Policy` HTTP response header. When a user clicks a link from your HTTPS site to another site, the browser sends a `Referer` header that includes the full URL (including query strings, paths, etc.). This leaks potentially sensitive information (e.g., session tokens in URLs) to external sites, especially if the external site is on HTTP.

**How to mitigate:**  
Add a `Referrer-Policy` header at the web server level (Apache, Nginx, or middleware). The recommended value is `strict-origin-when-cross-origin` — it sends the full URL to same-origin destinations, only the origin to cross-origin destinations, and nothing when going from HTTPS → HTTP.

```nginx
# Nginx example
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

### 2️⃣ Missing Content-Security-Policy (CSP) Header
- **Type:** Warning | **Priority:** Low | **Affects:** 100% of URLs (11 URLs)

**What it means:**  
No `Content-Security-Policy` header is set on any page. CSP is a powerful defense-in-depth mechanism that tells the browser which sources of content (scripts, styles, images, fonts, etc.) are trusted. Without it, the site is more vulnerable to **Cross-Site Scripting (XSS)** attacks — an attacker who injects a `<script>` tag can load and execute arbitrary JavaScript because the browser has no policy to reject it.

**How to mitigate:**  
Define and deploy a strict CSP header. Start with a **report-only** mode (`Content-Security-Policy-Report-Only`) to identify violations, then enforce once stable. A good starting point (adjust to your actual resources):

```nginx
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self';" always;
```

**Note:** The tool only checks for *existence* of the header, not its quality. You must manually verify the policy is tight enough.

---

### 3️⃣ Missing X-Content-Type-Options Header
- **Type:** Warning | **Priority:** Low | **Affects:** 100% of URLs (11 URLs)

**What it means:**  
The `X-Content-Type-Options: nosniff` header is absent. Without it, browsers may **MIME-sniff** — i.e., guess the content type when the `Content-Type` header is missing or ambiguous. An attacker could upload an image file that actually contains JavaScript (e.g., a polyglot file), and the browser might execute it as a script, leading to XSS.

**How to mitigate:**  
Set the header to `nosniff`, which forces the browser to trust the `Content-Type` header exclusively:

```nginx
add_header X-Content-Type-Options "nosniff" always;
```

Also ensure every response has an **accurate** `Content-Type` header (e.g., `text/html`, `application/json`, `image/png`).

### 5️⃣ Unsafe Cross-Origin Links (`target="_blank"` without `rel="noopener"`)
- **Type:** Warning | **Priority:** Low | **Affects:** 1 URL

**What it means:**  
A page uses `target="_blank"` on an external link without `rel="noopener noreferrer"`. In legacy browsers (a small minority, ~5% market share), the opened page gains access to `window.opener`, allowing it to redirect your page to a phishing site (tabnabbing attack). Today, most modern browsers (Chrome, Safari, Firefox, Edge) implicitly treat `target="_blank"` as `rel="noopener"`, so the practical risk is low but still worth fixing.

**How to mitigate:**  
Add `rel="noopener noreferrer"` to every `<a target="_blank">` link:

```html
<a href="https://example.com" target="_blank" rel="noopener noreferrer">Link</a>
```

For a CMS or build tool, add a global transform or use a plugin to automatically enforce this.

### 6️⃣ Missing X-Frame-Options Header
- **Type:** Warning | **Priority:** Low | **Affects:** 100% of URLs (11 URLs)

**What it means:**  
The `X-Frame-Options` response header is absent. This allows your pages to be embedded in `<iframe>`, `<frame>`, or `<object>` elements on other websites. Attackers can use this for **clickjacking** — overlaying invisible buttons/links on top of your page in an iframe, tricking users into clicking things they didn't intend.

**How to mitigate:**  
Add the header with value `DENY` (block all framing) or `SAMEORIGIN` (allow framing only from your own domain):

```nginx
add_header X-Frame-Options "SAMEORIGIN" always;
```

`SAMEORIGIN` is generally recommended unless you explicitly need third-party embedding (e.g., embeddable widgets).

### 8️⃣ Missing Canonical URL
- **Type:** Warning | **Priority:** Medium | **Affects:** 1 URL

**What it means:**  
One page has **no self-referencing canonical tag** (`<link rel="canonical" href="...">`). Without a canonical, Google must guess which URL is the "authoritative" version when it discovers multiple URLs pointing to the same content (e.g., `?utm_source=...`, `?page=1`, `http vs https`, `www vs non-www`). This can lead to unpredictable ranking signals and diluted link equity.

**How to mitigate:**  
- Add a `<link rel="canonical" href="[page URL]">` to every page's `<head>`, pointing to the definitive version.
- For CMS-based sites, ensure the canonical tag is automatically generated.
- Use the page's own URL as the canonical (self-referencing canonical) unless there's a specific reason to point to a different URL (e.g., a printer-friendly view pointing to the main article).
